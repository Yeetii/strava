# Filesystem Shard Store — retire Azure Blob from the highway tile path

Objective: replace the Blob-backed highway shard/index storage with a local filesystem store so the shard/tile path no longer needs a Blob connection. Branch: main (matching the other `odd/tasks/` docs). Delivery: uncommitted working-tree changes — the user owns commits and deploys. Test runner: `dotnet test strava.sln`.

## Specs

S1. "yes" — Authorized scope: turn the accepted Azure-Blob audit into an implementation task for a **filesystem-backed shard store**. The audit answered "What is left of azure blob store to migrate?" and found the remaining Blob dependencies are: (1) `BlobShardRepository` — the only real `IShardRepository`, (2) `HighwayZoomIndexService` index blobs and `BlobTileService`, (4) dead-but-blocking `BlobStorageConnection` / `AzureWebJobsStorage` wiring. Implement those three items. The scope is derived from that accepted audit, not a new user requirement; assumptions (root directory, config key names) are marked below.

S2. Acceptance: a filesystem `IShardRepository` preserves the exact current contract — `GetShardAsync`, `TryGetShardAsync`, `TryGetShardLastModifiedAsync`, `RebuildShardAsync`, `DeleteShardAsync`; the `z == canonicalZoom` guard; 404-equivalent → `null` / build-on-miss; empty-cached-shard Overpass re-validation; and the `onShardChanged` callback (best-effort, logged on failure). On-disk layout mirrors the Blob paths: `{z}/{x}/{y}.pbf` shards and `index/{z}/{x}/{y}.json` indexes. Index version (`IndexVersion = 4`), `z/x/y` validation, and `SyncIndexesForShardAsync` amendment semantics are preserved. No `Azure.Storage.Blobs` type remains in the *shard* wiring of `API/Program.cs` / `Backend/BackendServices.cs` or in the store-agnostic shard types (the race-organizers container creation left in `API/Program.cs` belongs to the out-of-scope organizer store) (`IShardRepository`, `IShardIndexStore`, `HighwayZoomIndexService`, `ShardBuilder`, `LocalShardFiles`, `FileSystem*` stores); Blob SDK usage is confined to the Blob provider implementations and its registration, which stay until decommission (assumption clarified 2026-11-17: the Blob provider must remain selectable as the default). The API and workers start without `BlobStorageConnection` when the filesystem shard store is selected. Assumption (config): `ShardStore__Provider = FileSystem | Blob` (Blob kept as default initially, mirroring `OrganizerStore`), `ShardStore__RootDir` → `/data/shards` in containers, mounted from host **`/opt/data/strava/shards`** via `SHARD_DATA_DIR` (user-specified 2026-11-17, see L10).

S3. Verification: `dotnet test strava.sln` passes with only pre-existing failures excepted (record them with evidence in Log); `deploy/scripts/verify-role-coverage.sh` is green; grep confirms no `BlobContainerClient`, `BlobStorageConnection`, or dead `BlobServiceClient` registration in the shard path. Test-first: one RED test per requested rule, then GREEN, then refactor. For each existing HTTP route sharing the changed code (highway tile endpoints, `/api/...` refresh), pin current behavior with tests; no unrequested behavior change. No integration harness exists — call this out as the known risk (see Risk).

S4. Out of scope (explicit, from the audit): audit item 3 (flip/remove `BlobOrganizerStore`, `export-organizers-to-blob`, `ExportOrganizersToDisk`), audit item 5 (verify/delete legacy `race-tiles` / `pois-shards` / `buildings-shards` / `shared-dictionaries` containers), Azure Tables (already replaced at HEAD), Cosmos, and deleting the Azure Blob resource (destructive, user-owned). ADR/plan Phase 8 step 2 sequences Blob after Tables and before Cosmos.
