# Deployment guide

Step-by-step instructions for getting the self-hosted stack running from scratch
and for the day-to-day deploy flow afterwards. For architecture details and
rollout decisions see [README.md](README.md).

**This setup is internal-only.** No ports are opened to the internet. The
workers connect outbound to Azure (Cosmos DB, Service Bus, Strava, etc.) but
the server itself is reachable only from your home network and your
[Tailscale](https://tailscale.com) tailnet. GitHub Actions deploys reach it
over the tailnet using Tailscale SSH. The Azure
API Function App stays up and continues handling all external traffic and the
Strava webhook during this phase.

---

## Prerequisites

- A Linux server on your home network (Ubuntu 22.04+ or Debian 12+)
- Docker Engine with the Compose plugin and `rsync` installed
  (`https://docs.docker.com/engine/install/`)
- SSH access as a user with `sudo`
- A Tailscale account (the free Personal plan is enough) — the deploy pipeline
  reaches the server through your tailnet
- The Azure connection strings, app secrets, and Strava credentials to hand

No DNS records, open firewall ports, or domain names are needed.

## First-time setup

### 1. Provision the server

SSH into the server, clone the repo to `/opt/repos/strava`, and run the
bootstrap script:

```bash
sudo mkdir -p /opt/repos && sudo chown "$USER" /opt/repos
git clone git@github.com:<your-org>/strava.git /opt/repos/strava
cd /opt/repos/strava
sudo ./deploy/scripts/bootstrap-server.sh
```

The repository stays in `/opt/repos/strava`. The bootstrap copies the
deployment files (Docker Compose and scripts) to `/opt/stacks/strava`
and generates a `.env` with a generated `AdminApiKey`. Docker (with the
Compose plugin) is assumed to be already installed and configured.

### 2. Fill in `.env`

```bash
nano /opt/stacks/strava/.env
```

Replace every `REPLACE` value:

| Key | Value |
| --- | --- |
| `IMAGE_NAMESPACE` | Your GitHub username/org, lowercase (e.g. `erikmagnusson`) |
| `CosmosDBConnection` | Cosmos DB connection string |
| `AzureSignalRConnectionString` | SignalR connection string |
| `StravaClientSecret` | From the Strava API app settings |
| `stravaVerifyToken` | The webhook verify token set in Strava |
| `AdminApiKey` | Generated by bootstrap; change if desired |
| `MistralStudioAgentId` | Mistral agent ID |
| `MistralStudioApiKey` | Mistral API key |
| `RACE_DATA_DIR` | Optional; host race-data directory (default `/opt/data/strava/races`) |
| `SHARD_DATA_DIR` | Optional; host highway-shard directory (default `/opt/data/strava/shards`) |
| `PMTILES_MEMORY_LIMIT` | Optional; pmtiles container memory cap (default `2g`) |
| `PMTILES_CPUS` | Optional; pmtiles container CPU cap (default `2.0`) |

Compose forces `OrganizerStore__Provider=FileSystem` and
`OrganizerStore__RaceDataDir=/data/races` on all self-hosted services so the
API, scrapers and the weekly build share one store. It also forces
`ShardStore__Provider=FileSystem` and `ShardStore__RootDir=/data/shards` on the
API and both workers, so no Blob connection string is needed. The pmtiles container
forces its tile output settings. Leave `COMPOSE_PROFILES=` empty for the first
deployment.

### 3. Allow the server to pull images from GHCR

If the GitHub packages are private, log in once on the server:

```bash
docker login ghcr.io -u <your-github-username>
# enter a personal access token with read:packages scope when prompted
```

If the packages are public this step is not needed.

### 4. Connect the server to Tailscale

Deploys reach the server through a Tailscale tailnet using
[Tailscale SSH](https://tailscale.com/kb/1193/tailscale-ssh), so no firewall
ports need to be opened or forwarded. Install Tailscale on the server and
enrol it as a **tagged** node with Tailscale SSH enabled:

```bash
curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up --ssh --advertise-tags=tag:server
```

If the server is already enrolled, re-run
`sudo tailscale up --advertise-tags=tag:server --force-reauth` and then
`sudo tailscale set --ssh`. Tagging matters: Tailscale SSH only allows
connections from tagged devices (the CI runner) to tagged devices.

Next, allow the CI runner to SSH in. In the Tailscale admin console under
**Settings → Access controls**, the policy needs both a network rule and an
`ssh` rule for `tag:ci → tag:server`:

```json
{
  "tagOwners": {
    "tag:server": ["<your-tailnet-user>"],
    "tag:ci": ["<your-tailnet-user>"]
  },
  "grants": [
    { "src": ["tag:ci"], "dst": ["tag:server"], "ip": ["*"] }
  ],
  "ssh": [
    {
      "action": "accept",
      "src": ["tag:ci"],
      "dst": ["tag:server"],
      "users": ["deploy"]
    }
  ]
}
```

Replace `deploy` in `users` with the SSH user configured as `SELFHOSTED_USER`
below (the user from bootstrap). `action: accept` is required — `check` mode
needs an interactive browser login, which CI cannot do.

### 5. Configure GitHub Actions secrets

In the GitHub repository go to **Settings → Environments → New environment**
and create an environment named `self-hosted`. Add these secrets:

| Secret | Value |
| --- | --- |
| `SELFHOSTED_HOST` | Server's Tailscale IP (100.x.y.z) or MagicDNS name |
| `SELFHOSTED_USER` | The SSH user (same as `DEPLOY_USER` used during bootstrap); must be listed in the `ssh` rule `users` |
| `TS_OAUTH_CLIENT_ID` | Tailscale OAuth client ID for CI nodes |
| `TS_OAUTH_SECRET` | Tailscale OAuth client secret |

Create the OAuth client in the Tailscale admin console under
**Settings → OAuth clients**
(<https://console.tailscale.com/settings/oauth>):

- Scope: **Auth keys — writable** (`auth_keys`)
- Tags: `tag:ci`

The GitHub-hosted runner joins the tailnet as an ephemeral, tagged node
(`tag:ci`, hostname `strava-gh-deploy`) for the duration of the deploy job and
is removed automatically afterwards. Tailscale SSH authenticates the
connection, so no SSH keys are stored in GitHub and no ports need to be
exposed to the internet.

### 6. Start the stack

```bash
cd /opt/stacks/strava
docker compose pull
docker compose up -d --wait
docker compose ps
```

All containers should reach `healthy` or `running` within about 2 minutes.

### 7. Seed race data (one-off)

The `pmtiles` container runs a weekly race-tile build from the host directory
`RACE_DATA_DIR` (`/opt/data/strava/races`, mounted at `/data/races`) shared with `api`.
Create it on the server with `mkdir -p /opt/data/strava/races`, then populate it once from the existing Blob
store, from a machine that has the Blob connection string configured:

```bash
dotnet run --project Tools/CosmosBulkDelete.csproj -- export-organizers-to-disk --data-dir /data/races
```

This is a `Tools` command, not part of the image. After seeding, the pmtiles
container needs no Azure configuration — it reads organizers and writes the
archive entirely on disk (`/data/races/tiles/trails.pmtiles`, served by `api`
at `/tiles/trails.pmtiles`). Verify a build with:

```bash
cd /opt/stacks/strava
docker compose run --rm pmtiles build-race-tiles-from-organizers
docker compose ps pmtiles
```

### 8. Seed the highway shard directory (one-off)

The API and both workers store highway shards (`{z}/{x}/{y}.pbf`) and zoom indexes
(`index/{z}/{x}/{y}.json`) under `SHARD_DATA_DIR`
(`/opt/data/strava/shards`, mounted at `/data/shards`) — next to the race data and
its PMTiles archive under `/opt/data/strava/races`. Create it once, writable by the
containers:

```bash
mkdir -p /opt/data/strava/shards
```

No Blob seed is needed. A missing shard is rebuilt from Overpass on first request
and cached in this directory; zoom indexes are built from those shards.

## Normal deploys (after first-time setup)

Pushing to `main` triggers the `Deploy self-hosted backend` workflow
automatically whenever `API/`, `Backend/`, `PmtilesJob/`, `Shared/`, `deploy/`,
or `Directory.Build.props` change. The workflow:

1. Verifies every Backend function is assigned to a container
2. Builds and pushes the `peakshunters-api`, `peakshunters-backend` and
   `peakshunters-pmtiles` images to GHCR tagged with the commit SHA
3. Connects the runner to the tailnet and rsyncs `deploy/` to the server over
   Tailscale SSH (without touching `.env`)
4. Pulls the new images and restarts the stack with a 5-minute health-check
   timeout
5. Rolls back to the previous image tag automatically if startup fails

No manual steps are needed for a normal deploy.

### Manual deploy of a specific tag

```bash
ssh <user>@<server-ip>
cd /opt/stacks/strava
./scripts/deploy.sh <commit-sha-or-tag>
```

### Rollback

```bash
ssh <user>@<server-ip>
cd /opt/stacks/strava
./scripts/deploy.sh <previous-commit-sha>
```

The previous tag is written to `.env.previous` before each deploy:

```bash
grep IMAGE_TAG /opt/stacks/strava/.env.previous
```

## Enabling workers

Workers are off by default so the self-hosted stack can be validated without
competing with Azure for Service Bus messages or timer jobs.

### Enable queue/change-feed workers (competing consumers with Azure)

Edit `.env` on the server:

```
COMPOSE_PROFILES=workers
```

Then apply:

```bash
cd /opt/stacks/strava
docker compose up -d --wait
```

Both the Azure Backend app and `worker-heavy` will now consume from the same
Service Bus queues. Service Bus delivers each message to only one consumer, so
load is shared rather than duplicated — safe for gradual validation.

### Enable scheduled jobs (timers)

Timer functions are not competing consumers — both Azure and the self-hosted
worker would fire each schedule independently. **Disable the matching timer
functions in the Azure Backend app first**, then:

```
COMPOSE_PROFILES=workers,schedules
```

```bash
cd /opt/stacks/strava
docker compose up -d --wait
```

## Day-to-day operations

### View logs

```bash
cd /opt/stacks/strava
docker compose logs -f --tail=200
# single service
docker compose logs -f --tail=200 worker-heavy
```

### Restart a single service

```bash
docker compose restart worker-heavy
```

### Check container status

```bash
docker compose ps
```

### Rebuild race tiles now

The `pmtiles` container normally just runs its weekly scheduler. To build once
immediately (for example after seeding or a data fix):

```bash
docker compose run --rm pmtiles build-race-tiles-from-organizers
```

It reads and writes the shared host directory at `/opt/data/strava/races`; `api` then serves the new
archive at `/tiles/trails.pmtiles`. Add `--write-transparency` to also write
assembled race JSON to the volume.

### Monitoring

Container and host metrics are covered by Beszel. Application logs are via
`docker compose logs` (see below).

## Troubleshooting

**Container stuck in `starting` / health check failing**

The Functions host takes up to 2 minutes to start. Check the logs:

```bash
docker compose logs --tail=50 worker-heavy
```

A missing or wrong connection string is the most common cause.

**GitHub Actions can't SSH to the server**

The runner joins the tailnet in the **Connect runner to the tailnet** step,
then authenticates with Tailscale SSH. Check, in order:

- The **Connect runner to the tailnet** step succeeded. It waits up to 3
  minutes for the server to become reachable; while the job runs, the
  ephemeral `strava-gh-deploy` node is visible in the Tailscale admin console
  under **Machines**.
- The server is enrolled and tagged, and advertises Tailscale SSH:
  `sudo tailscale up --ssh --advertise-tags=tag:server`.
- The tailnet policy has **both** the `grants` rule and the `ssh` rule for
  `tag:ci → tag:server`, and the `ssh` rule's `users` list includes
  `SELFHOSTED_USER`.
- The OAuth client has the writable `auth_keys` scope and the `tag:ci` tag,
  matching the `tags` value in the workflow.
- `SELFHOSTED_HOST` is the server's Tailscale IP (100.x.y.z) or MagicDNS
  name, not its LAN address. Tailscale SSH only works on port 22.

**`SELFHOSTED_HOST and SELFHOSTED_USER must be configured` or `TS_OAUTH_CLIENT_ID and TS_OAUTH_SECRET must be configured`**

The GitHub Environment secrets are missing or the environment name does not
match `self-hosted` exactly.

**Functions key errors (401 on admin endpoints)**

Access the Functions admin API over an SSH tunnel:

```bash
ssh -L 7071:127.0.0.1:80 <user>@<server-ip>
# the api container's port 80 is now at localhost:7071
curl http://localhost:7071/admin/host/keys
```
